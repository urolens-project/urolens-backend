## D — docstrings (349 total): consistent with "docstring pass ran, completed, scoped to `src/urolens/`"

Split by directory tells the real story:

- **`src/urolens/` (the docstring pass's actual scope): 183 violations, and every single one is a formatting nitpick — zero missing-docstring violations.** `D205` missing-blank-line-after-summary (136) — Google convention wants a blank line between the one-line summary and any further description; most docstrings from the pass put the detail right after the summary instead. `D417` undocumented-param (23) and `D107` undocumented-public-init (20) — the pass added class docstrings but not always a dedicated `__init__` docstring or a fully param-complete `Args:` list. `D415`/`D105` (3+1) are minor punctuation/magic-method gaps. **No `D100`/`D101`/`D102`/`D103`/`D104` (missing module/class/method/function/package docstring) at all in `src/urolens/`** — confirms the pass's actual content (docstrings exist) matches its own claims; what's left is pydocstyle's stricter formatting rules, which the pass never targeted.
- **`tests/` (91 violations) and root scripts + `alembic/` (75 violations) were never in the docstring pass's scope.** These are dominated by real missing-docstring categories (`D102`/`D103`/`D101`/`D100` — test methods/functions/classes and script functions with no docstring at all), which is expected for test files (docstrings on `test_*` functions aren't a convention this codebase — or most codebases — follow) and for one-off scripts.

**Verdict: consistent with "docstring pass ran and completed" for its actual scope, not "not started" or "partially done."** If `src/urolens/` had skipped files, this would show up as `D100`/`D103` hits there — it doesn't.

## S — security patterns (194 total): read this one closely, per the project's history

Six distinct patterns, by rule code (not occurrence count):

- **`S101` assert (169 — the overwhelming majority of the S total).** 100% in `tests/`, 0 in `src/urolens/` or root scripts (verified directly). This is pytest's own idiom (`assert x == y` is how pytest assertions work) — not a real finding, just the rule firing on every test file by design. This single pattern accounts for 87% of the entire S count.
- **`S105` hardcoded-password-string (6).** All confirmed false positives on inspection: 2 are `token_type: str = "Bearer"` in `schemas/auth.py` (a standard OAuth token-type string, not a secret), 4 are test-fixture variables literally named `password`/`MEDTECH_PASSWORD` holding known test strings in `tests/test_auth_service.py` and `test_image_upload.py`. **No real hardcoded secret found** — the JWT-placeholder-fallback class of bug this project was flagged for previously has already been fixed (see earlier changelog entries); this scan found nothing new in that category.
- **`S311` suspicious-non-cryptographic-random-usage (13).** 2 are real, in production code: `random.randint(...)` used for UID-suffix generation in `services/lab_request_service.py` and `services/specimen_service.py` (`REQ-`/`SMP-` style IDs). Worth a design note, not an incident — these UIDs need uniqueness (checked against the DB before use) and human-readability, not unpredictability, so non-cryptographic randomness is an intentional, reasonable choice here — but flagging it is exactly what this rule is for, and it's a fair question for whoever owns ID-generation to confirm. The other 11 are in `test_image_upload.py`, a manual dev script generating fake test data.
- **`S110`/`S112` try-except-pass / try-except-continue (3 + 3 = 6).** All in production code (`core/audit_logger.py`, `services/patient_service.py`, `services/physician_service.py`, `services/physician_result_service.py`) — and all are the same intentional, already-documented pattern from this codebase's own design: audit-log writes must never break the caller's main transaction (swallow and move on), and PII-decryption failures during a search skip that one row rather than crash the whole request. Not new findings — these are pre-existing, deliberate design decisions, surfaced here for visibility, not as bugs.

**Bottom line: of 194 S hits, ~182 (94%) are test-suite noise or confirmed false positives; the remaining ~12 are already-known, deliberate patterns.** Nothing in this scan surfaced a new secret-handling or injection-class issue. This is a reassuring result given the project's history, not a concerning one — but it's exactly the category worth re-running after every future change, since it's cheap to check and this is precisely the class of bug that shipped once before.

## B — bugbear (121 total): mostly a known FastAPI-pattern false positive

- **`B008` function-call-in-default-argument (117 — 97% of the B total).** Grep-confirmed at least 99 of these are `Depends(...)` in FastAPI route signatures — the standard, required dependency-injection pattern for this framework (`def route(db: AsyncSession = Depends(get_db))`), not a real bug. A few are `Query(...)`/`Body(...)`/`File(...)`/`Form(...)`, same story. This is a well-known Ruff/FastAPI interaction; a future pass could silence it properly via `[tool.ruff.lint.flake8-bugbear] extend-immutable-calls`, but that's a config change beyond this task's scope.
- **`B904` raise-without-from-inside-except (3)**, in `core/rbac.py`, `services/patient_auth_service.py`, `services/result_confirmation_service.py` — real findings: re-raising inside an `except` without `raise ... from err`/`from None` loses the original exception chain. Worth a look, not fixed here.
- **`B017` assert-raises-exception (1)**, `tests/test_auth_service.py:74` — `pytest.raises(Exception)` is too broad; a real (if minor) test-quality nit.
